================================================================================
القسم 1 — نظرة عامة
================================================================================
«أثير» نظام ERP محاسبي إداري للفنادق يعمل بثلاثة أوضاع من نفس قاعدة الكود:
  (أ) محلي On-Premise: خادم داخل الفندق، يعمل 100% بدون إنترنت.
  (ب) سحابي SaaS: Multi-Tenant مركزي.
  (ج) هجين Hybrid: محلي كامل + مزامنة ثنائية مع السحابة (تقارير مركزية،
      نسخ احتياطي خارجي، إدارة تراخيص، دعم عن بُعد).

مبدأ التصميم الأعلى: «نفس النواة، ثلاثة أوضاع نشر»
  الكود لا يعرف وضع تشغيله إلا من ملف إعداد deployment.mode.
  كل الاختلافات (قاعدة البيانات، المصادقة، الترخيص، المزامنة) خلف واجهات
  (Interfaces) قابلة للتبديل — ممنوع كتابة منطق مربوط بوضع نشر محدد داخل
  الوحدات الوظيفية.

لغة التوثيق والتسمية: الكود والجداول بالإنجليزية، الواجهة عربي أولاً ثم إنجليزي.

بدائل دُرست ورُفضت مع السبب:
  - Node/NestJS: ممتاز لكن نظام الأنواع الأضعف خطر على الثوابت المالية.
  - Desktop WinForms/WPF: ربط البواجه بمنصة واحدة + عبء صيانة واجهتين.
  - MySQL: أضعف في القيود المرجعية المعقدة والـ Partitioning مقابل Postgres.

قواعد الاعتماد (Dependency Rules — يفحصها اختبار معماري آلي):
 1) الاعتماد للداخل فقط: API → Application → Domain/Core ← Infrastructure.
 2) نواة المحاسبة لا تستورد أي وحدة تشغيلية (غرف/POS...). العكس مسموح عبر الأحداث.
 3) ممنوع تجاوز الطبقات (Controller يستدعي DbContext مباشرة = رفض مراجعة).
 4) كل وحدة تشغيلية مكتفية ذاتياً بحدودها (Module Boundary) وتتواصل بأحداث.

قائمة الوحدات (Modules):

  Hotel (Rooms/Reservations/Folio/NightAudit) | POS | Inventory/Purchasing
  HR.Payroll | FixedAssets | Reports/BI | VendorPanel (سحابي فقط، منفصل)

القسم 4 — أوضاع النشر بالتفصيل
================================================================================
4.1 محلي On-Premise:
  جهاز خادم بالفندق (أو حاسوب المدير) عليه: Backend + PostgreSQL + Sync Agent
  (معطل) + License Agent. الوصول من أجهزة الشبكة المحلية عبر المتصفح HTTPS
  بشهادة داخلية. يعمل بلا إنترنت إطلاقاً؛ تحقق الترخيص محلي مع مهلة سماح.

4.2 سحابي SaaS:
  ┌─ Load Balancer (TLS) ─ API Replicas (Stateless)
  ├─ PostgreSQL Managed (أساسي + Read Replica للتقارير)
  ├─ Redis (جلسات/أقفال) ─ Object Storage مشفر (مرفقات/نسخ)
  └─ Vendor Panel (بوابة الشركة) + License Authority + Telemetry
  عزل المستأجرين: tenant_id بكل جدول + Row-Level Security في Postgres
  (سياسة FORCE RLS) = عميل لا يمكنه رؤية غيره حتى لو أخطأ الكود.

4.3 هجين Hybrid:
  التثبيت المحلي = «الأصل التشغيلي اليومي»؛ المزامنة ترفع التغييرات للسحابة
  (Outbox) وتنزّل ما يلزم (Inbox: التراخيص، إعدادات مركزية، قوالب). السحابة
  تقدم للعميل: لوحة تقارير موحدة (متعدد الفروع)، نسخة احتياطية خارجية،
  ودعم عن بُعد عبر نفق مؤقت مفوَّض. حالة انقطاع الإنترنت: يستمر العمل
  محلياً 100% وتتراكم الأحداث ثم تُرفع عند العودة (انظر ملف 09).

مصفوفة الفروقات خلف الواجهات:
  الخدمة        | محلي            | سحابي              | هجين
  --------------|-----------------|--------------------|------------------
  قاعدة البيانات| PG محلي (أو SQLite)| PG مركزي RLS    | PG محلي + مزامنة
  المصادقة      | هوية محلية      | هوية سحابية MFA    | محلية + ربط اختياري
  الترخيص       | ملف موقع + مهلة | تحقق لحظي          | ملف موقع + مزامنة إلغاء
  المزامنة      | معطلة           | غير مطلوبة داخلياً  | فعالة دائماً
  النسخ الخارجي | مجلد درجة/شبكة  | تلقائي مركزي        | محلي + رفع للسحابة

القسم 5 — اتفاقيات بناء الكود (إلزامية)
================================================================================
- Monorepo واحد: /backend /frontend /desktop /sync /vendor-panel /docs /tests
- إصدار دلالي SemVer للمنتج ورقم Migration تسلسلي لا يُعاد استخدامه.
- كل ميزة خلف Feature Flag (قابلة للإطفاء لكل عميل/بيئة).
- كل API موثق OpenAPI تلقائياً من الكود.
- Migrations تقدمية فقط Forward-Only؛ التراجع بنسخة + Migration تعويضية.
- فحص CI إلزامي قبل الدمج: Build + Unit + Integration (قاعدة حقيقية عبر
  Testcontainers) + فحص الثوابت المحاسبية + Lint + فحص أسرار (Gitleaks).
- Log منظم بلا بيانات حساسة (ممنوع تسجيل كلمات سر/بطاقات/مفاتيح ترخيص كاملة).
- معيار الزمن: تخزين UTC دائماً + عرض بتوقيت الفندق؛ «تاريخ العمل» Business Date
  يحدده التدقيق الليلي لا ساعة الجهاز (حرج: تغيير ساعة الجهاز لا يكسر اليومية).

القسم 6 — الأداء والتوسع
================================================================================
- هدف SaaS: 500 فندق، 5,000 مستخدم متزامن، P95 للقراءات < 300ms.
- تقارير ثقيلة عبر Read Replica + جداول مجمعة تُحدَّث ليلياً (يُتحقق منها
  مقابل القيود — انظر ملف 02 قسم 1.4).
- Partitioning شهري على: journal_entry_lines, audit_log, sync_events.
- كل استعلام يمر بالـ tenant_id تلقائياً (Global Query Filter).
- حجم مكتبة الثوابت: الحسابات والعملات تُحمَّل مرة وتُخزن بذاكرة التطبيق
  مع إبطال مؤقت قصير.

================================================================================
القسم 7 — القرارات المعمارية المسجلة (ADR مختصرة)
================================================================================
ADR-01 Single codebase لكل أوضاع النشر (أعلاه).
ADR-02 PostgreSQL موحد: توحيد دلالات المعاملات بين المحلي والسحابي أهم
        من بساطة SQLite؛ SQLite خيار «حاسوب واحد صغير» عبر DAL فقط.
ADR-03 Event-Driven Accounting (ملف 02 §6): فصل التشغيل عن المحاسبة،
        idempotency أصيل، أساس جاهز للمزامنة.
ADR-04 Outbox Pattern لكل حدث خارجي (مزامنة/إشعارات) — لا نشر خارج المعاملة.
ADR-05 أرصدة مشتقة لا مخزنة (قابل للكسر) مع كاش قابل لإعادة البناء والتحقق.
ADR-06 UUID لكل المفاتيح الأساسية: مزامنة بلا اصطدامات أرقام تسلسلية
        بين العقد؛ التسلسلات البشرية (أرقام القيود/الفواتير) لكل عقدة وبادئة موقع.
ADR-07 لا Soft-Delete في القيود والأحداث المالية إطلاقاً (Append-Only)؛
        السجلات التشغيلية الأخرى Soft-Delete مع أثر تدقيق.
ADR-08 Vendor Panel تطبيق مستقل تماماً (نطاق/مستودع أسرار منفصل) مع API
        محدود جداً للأنظمة العميلة (نبض ترخيص، مزامنة، تذاكر) — انظر ملفات 07/08.
