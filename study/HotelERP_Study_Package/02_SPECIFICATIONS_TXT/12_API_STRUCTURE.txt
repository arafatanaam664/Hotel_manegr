================================================================================
القسم 1 — الاتفاقيات العامة
================================================================================
- التوثيق: Authorization: Bearer <JWT> (15 د) + Refresh بالدوران.
- التعريف: tenant من الـ JWT (لا يقبل tenant_id من العميل إطلاقاً)، الفرع
  من JWT أو ترويسة X-Branch-Id مع التحقق من نطاق المستخدم.
- الترويسات: X-Request-Id (يُرجع ويُسجل)، Idempotency-Key إلزامي لكل POST
  مالي/مستندي (يمنع ازدواج الإرسال عبر الشبكات الضعيفة — انظر jobs).
- الترقيم: cursor-based (?cursor=&limit≤200) — لا offset للجداول الكبيرة.
- الزمن: كل الطوابع RFC 3339 UTC؛ التواريخ التجارية business_date صريحة.
- الأخطاء: مظروف موحد:
  { "error": { "code": "ACCOUNTING.UNBALANCED_ENTRY", "message_ar": "...",
    "message_en": "...", "details": {...}, "trace_id": "..." } }
  رموز النطاقات: AUTH.*, RBAC.*, VALIDATION.*, ACCOUNTING.*, HOTEL.*,
  POS.*, INV.*, PAYROLL.*, LICENSE.*, SYNC.* — موثقة بجدول أكواد قابل للبحث.
- الإصدارات: /api/v1 ثابت لعقدة؛ التغيير الكاسر = /api/v2 بجانبه (لا كسر
  لعميل قديم أبداً داخل المنتج).

القسم 2 — خريطة المسارات (الرئيسية، غير شامل)

  POST /api/v1/auth/logout         POST /api/v1/auth/mfa/enroll|verify
  GET  /api/v1/auth/sessions       DELETE /api/v1/auth/sessions/{id}

القسم 4 — معايير القبول
================================================================================
1) كل مسار في OpenAPI المولَّد له: مخطط طلب/رد، أكواد أخطاء، صلاحية مطلوبة.
2) 100% من المسارات الكاتبة خلف: تحقق مخطط + RBAC + Idempotency حيث يلزم.
3) لا مسار يقبل tenant_id من العميل — اختبار سلبي آلي لكل مسار.
4) عقود اختبار (Contract Tests) بين الواجهة والـ API تعمل بالـ CI.
