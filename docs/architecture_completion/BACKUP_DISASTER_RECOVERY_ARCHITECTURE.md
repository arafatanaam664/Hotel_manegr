# BACKUP & DISASTER RECOVERY ARCHITECTURE — معمارية النسخ الاحتياطي والتعافي من الكوارث (المخرَج H)

> **المرحلة 2ب — تصميم فقط؛ لا كود.** التاريخ: 2026-08-07 | تغطي المتطلبات: 10, 11, 12
> **القواعد الملزمة من المالك:** النسخ ليس زراً شكلياً إطلاقاً؛ لا نسخة تُعتمد دون تحقق فتح حقيقي؛ الخصوصية أولاً — الشركة لا ترى بيانات أعمال العميل. **العقيدة الذهبية: نسخة لم تُختبر استعادتها = لا نسخة** (درس R-A).

---

## 1. المبادئ الحاكمة
1. **3-2-1:** ثلاث نسخ، وجهتان مختلفتان وسيطان، واحدة خارج المبنى (USB متسرب/شبكة/سحابة بعقد).
2. **مشفرة دائماً:** لا تغادر النسخة القرص المحلي إلا مشفرة AES-256-GCM بمفتاح العميل (§9).
3. **التحقق = فتح:** وجود ملف وحجمه لا يثبت شيئاً؛ التحقق فتح قاعدة النسخة + عدّات مرجعية + hash.
4. **الاستعادة عملية مقيدة:** موافقة مزدوجة + تأكيد كتابي — لأنها الفعل الأكثر تدميراً المحتمل.
5. **مشتقة من النشر (اتساق الزوج Deployment↔Backup — MASTER §10):** السياسة الافتراضية تُشتق آلياً من `deployment_type` (جدول §3) ولا يبنى مسار مستقل.

## 4. التشغيل اليومي (آلي بلا تدخل)
جدولة خادمية (نواة ENG-SCH مصممة بملف 07/17) تشغّل: نسخ يومي بالوقت الخامل → تحقق فوري → أسبوعياً (الأحد) **اختبار استعادة آلي** → شهرياً تقرير صحة نسخ للمالك. فشل أي منها يرفع تنبيهاً P1-حرجاً (NTF-SYS-03) بثلاث قنوات + بطاقة حمراء بلوحة الصحة (SCR-MON-001) + سطر بحالة النظام للشركة عبر النبض.

## 5. التحقق واختبار الاستعادة (الفرق بين «ملف» و«نسخة»)
1. **تحقق فوري لكل نسخة:** فك تشفير لنسخة مؤقتة → فتح القاعدة فعلاً → تشغيل عدّات: (عدد القيود/الحجوزات/الفواتير = قيم manifest) → hash → ختم VERIFIED (آلة §4.5: لا VERIFIED بلا فتح).
2. **اختبار استعادة دوري آلي (restore_tests — إعادة استخدام من 13-B):** استعادة كاملة لمجلد فحص معزول → إقلاع تطبيق فحصي عليها → قيد ذهبي استعلامي (ميزان اليوم السابق يطابق آخر لقطة مدقق ليلي موقعة ✅ WIZ-002-7) → PASSED/FAILED؛ الفشل P1-حرج (§4).
3. **ممنوع:** اعتماد «pipe نجح» أو «الحجم معقول» كدليل؛ كل واجهة تعرض «آخر نسخة موفقة + نتيجة آخر اختبار استعادة» معاً — لا أحدهما وحده.

## 6. سير عمل النسخ الكامل (المخرَج H — المتطلبات 10/12)
`1) تفعيل السياسة: معالج WIZ-007 (وجهتان إلزاماً + GFS + مفتاح تشفير مولّد ويُسلَّم للعميل بظرف/قناة أمانة) ─ 2) الجدولة تعمل تلقائياً يومياً خامل الوقت ─ 3) لقطة متسقة → ضغط → manifest → تشفير ─ 4) توزيع لكل الوجهات مع استئناف ─ 5) تحقق فوري بالفتح والعدّات ─ 6) تسجيل backup_jobs وتحديث بطاقة الصحة ─ 7) عند الفشل: تنبيه P1-حرج بثلاث قنوات + محاولة إعادة مجدولة ─ 8) أسبوعياً: اختبار استعادة آلي معزول (restore_tests) ─ 9) شهرياً: تقرير «صحة الحماية» للمالك (نجاح/فشل/أقدم نقطة استعادة/استهلاك تخزين) ─ 10) عند الكارثة: سير الاستعادة §7 بموافقة مزدوجة.` — **RPO الرسمي: ≤24 ساعة محلي (نسخ يومي)، ≤1 ساعة هجين/سحابي (أحداث المزامنة تُعاد تطبيقها فوق آخر نسخة)، RTO: ≤ ساعتين لخادم بديل جاهز، ≤ يوم عمل شراء عتاد جديداً** — وتُعلن هذه الأهداف التزاماً تعاقدياً.

## 7. سيناريوهات الاستعادة الأربعة (Runbooks مختصرة)
| السيناريو | الخطوات | الضوابط الحاكمة |
|---|---|---|
| S1 حذف/تلف بيانات جزئي | استعادة آخر نسخة لمجلد فحص → تصدير السجلات المفقودة → استيراد موثق إلى الحيّة بتوقيع حدث | لا استيراد صامت: حزمة إصلاح مرئية بالتدقيق |
| S2 تلف كامل للقاعدة (القرص حيّ) | إيقاف الخدمة → استعادة آخر VERIFIED → فتح وتحقق عدّات → تشغيل | موافقة مزدوجة (مالك + مدير نظام) + DLG تأكيد كتابي («اكتب: استعادة») + بقاء التالف مؤرشفاً جانباً |
| S3 فقدان الخادم كله (عتاد جديد) | تثبيت نظيف → استعادة النسخة المشفرة بمفتاح العميل → **إعادة ربط بصمة ترخيص** بسير موثق (LIC §13 — بصمة الجهاز الجديد + محضر نقل) → تحقق → تشغيل | لا يُفعَّل تشغيل كامل قبل ربط البصمة؛ النسخة السحابية (إن وُجدت) تُستدعى بعميل العقد |
| S4 هجوم تخريبي/Ransomware | عزل → استعادة من USB/نسخة خارجية **سابقة للإصابة** (GFS يسمح بالرجوع أسابيع) → تحقق → بلاغ | مفاتيح التشفير ليست على الخادم المخترق؛ توصية وجهة WORM (كتابة مرة) للشبكية |

## 8. التعافي من الكوارث — الخطة المعلنة (المتطلب 12)
- **المخزون:** خادم بديل مُوصى به لكل عميل كبير؛ صورة تثبيت جاهزة بقناة USB رسمية.
- **الأدوار:** مالك فندق (قرار) + مدير نظام (تنفيذ) + شركة (ربط ترخيص/دعم) — كل دور له صلاحية مرقّمة (E/MASTER §5).
- **التدريب:** «تمرين كارثة» سنوي إلزامي تعاقدياً للعملاء التجاريين: استعادة S2 كاملة بتوقيت — يُسجل زمناً ويُثبت تحقق RTO المعلن (§6) ويُحفظ محضره.
- **التكامل مع التحديثات:** كل تحديث يفرض BACKED_UP (§DEPLOYMENT-6) ⇒ نقطة رجوع مضمونة حديثة دائماً.

## 9. الخصوصية وعزل البيانات (المتطلب 11) — طابعة ما يغادر الفندق
| ما الذي يصل الشركة؟ | أبداً | بعقد REMOTE_BACKUP فقط |
|---|---|---|
| بيانات الأعمال (حجوزات/نزلاء/مالية) | — | ✗ كتل نسخ **مشفرة بمفتاح العميل** — الشركة لا تملك فتحها |
| مفاتيح التشفير | ✗ تبقى عند العميل | ✗ (Escrow اختياري بعقد مستقل موقّع وإجراء تسليم مزدوج — قرار تجاري لاحق) |
| الميتاداتا التشغيلية (نبض: إصدار/صحة مزامنة/عدادات مجمعة/آخر نسخة موفقة/آخر اختبار استعادة) | — | ✅ هذا كل ما تراه بطاقة 360° (MASTER §6) |
| التراخيص والإبطالات والأحداث الترخيصية | — | ✅ (لأنها عقود — لا بيانات أعمال) |

**الضوابط:** مفتاح AES لكل عميل (تسرب عميل ≠ تسرب الجميع — T-07)؛ مفاتيح تُدار عند العميل وتُفقَد بفقدانه (تحذير صريح بالمعالج خطوة 27؛ فقدان المفتاح بلا escrow = استحالة استعادة سحابية — مقايضة خصوصية معلنة)؛ حذف نسخ سحابية عند إنهاء عقد بمحضر إتلاف موقّع خلال مهلة تعاقدية؛ عزل تخزين سحابي بحدود tenant_id الصفّية نفسها ✅.

## 10. تهديدات النسخ تحديداً (تكمل L)
| التهديد | الضابط |
|---|---|
| سرقة ملف نسخة | مشفرة GCM بمفتاح غائب عن الملف؛ بلا فائدة للسارق |
| حذف نسخ انتقامي (داخلي) | حذف نسخ يدوياً عملية مزدوجة التوثيق + بقاء وجهة ثانية حيّة + حدث تدقيقي |
| تعديل manifest لإخفاء تلف | manifest موقّع داخلياً + اختبار الاستعادة المعزول يكشف أي تناقض عدّات |
| استعادة خبيثة لاستبدال واقع | S2 بموافقة مزدوجة + أرشفة الحيّة قبل الاستبدال + سجل قرار |
| ترخيص على الجهاز البديل | إعادة ربط بصمة موثقة (S3) — لا التفاف باسم الاستعادة (LIC §13) |
