# ARCHITECTURE CHANGE PLAN — خطة تغييرات المعمارية التجارية (المخرَجات M · N · O · P)

> **المرحلة 2ب — تصميم فقط؛ لا كود نُفِّذ.** التاريخ: 2026-08-07 | تغطي المتطلبات: 27 (M قاعدة البيانات) · 28 (N الـ API) · 29 (O الواجهات) · P (خطة الترحيل والدمج بالخارطة)
> **مبادئ حاكمة:** (1) كل تغيير قاعدة **additive فقط** — الترخيص تحديثاته آمنة التراجع (آلة §4.7). (2) **توافق رجعي صارم:** تراخيص v1 المصدرة تعمل بلا إعادة إصدار (قارئ v2 يفترض الآمن عند غياب حقول v2 — LIC §3). (3) لا يتيم: كل واجهة برمجية لها جدول/مصدر، وكل جدول له واجهة أو سبب مكتوم موثق (زوج API↔Database ✓). (4) **تصالُح مع مرحلة 2أ:** `backup_jobs` و`restore_tests` معرّفتان بملف 13-B (ضمن الـ28 جدولاً المستهدفة) — نعيد استخدامهما ولا نعيد تعريفهما.

## M — تغييرات قاعدة البيانات (المتطلب 27)

### M-1. جداول جديدة — قاعدة الفندق (Tenant) — 11 جدولاً
| الجدول | الغرض | العلاقات/مفاتيح حاكمة | يخدم |
|---|---|---|---|
| `installation_sites` | موقع/جهاز التثبيت المرتبط بالترخيص | tenant 1:1 حالياً (N مستقبلاً بخوادم إضافية)؛ لقطة بصمة؛ حالة؛ آخر نبض | F، MASTER §3 |
| `deployment_profiles` | ملف النشر الرسمي | tenant 1:1؛ type ∈ {ON_PREM,CLOUD,HYBRID}؛ sync_enabled؛ backup_policy_id→؛ update_channel | متطلب 1 |
| `provisioning_runs` + `provisioning_run_steps` | سير التثبيت المرحلي الموثق (آلة §4.4) | run←client_ref/hotel؛ step: رقم/الحالة/محضر/موقّع؛ حالة ختم نهائية | F §3 |
| `config_templates` | قوالب التهيئة المعتمدة | code إصدار مرقم؛ محتوى JSON موقّع الشركة؛ نطاق تطبيق | §Templates DEPLOYMENT |
| `license_events` | سجل أحداث ترخيص فندقي غني (فوق التدقيق العام) | tenant؛ serial تصاعدي مرآة الشركة؛ type؛ before/after state؛ actor | LIC §14 |
| `backup_policies` | سياسة نسخ قابلة استعلام وتدقيق | tenant 1:1؛ وجهات JSON؛ GFS؛ مفتاح مرجع (لا مفتاح نفسه!)؛ حدود دنيا COMPANY_ONLY | BACKUP §2-3 |
| `backup_jobs` · `restore_tests` | سجلات التنفيذ والاختبار | **إعادة استخدام كما عرّفتهما خطة 13-B — لا ازدواج** | BACKUP §5 |
| `update_packages` + `update_runs` | حزم منزلة/موقعة وحالات التطبيق | package: version/hash/قناة؛ run: آلة §4.7 كاملة + سبب تراجع | §Updates DEPLOYMENT |
| `support_sessions` + `support_session_events` | جلسات دعم بموافقة | session: نطاق/مدة/حالة/موافق عليه (user_id)؛ event: شاشة/فعل/لقطة قرار | §Support DEPLOYMENT |

**فهارس إلزامية جديدة:** `license_events(tenant_id, serial)` · `backup_jobs(tenant_id, started_at)` · `update_runs(tenant_id, created_at)` · `support_sessions(tenant_id, status)` — وتنضم لخطة التقسيم الشهري المؤجلة (ملف 13 §F) عند PG الإنتاجي.
**لا جداول لـEditions/FeatureSets جهة الفندق:** سجل القدرات = **كود موقّع بالإصدار** (registry) + الحمولة الموقعة المخزنة ✅ — قرار معماري موثق: لا نسخة تُحرَّر محلياً = لا عبث (T-03).

### M-2. جداول/أعمدة جديدة — قاعدة الشركة (Vendor) — 4 جداول + مجموعتا أعمدة
| العنصر | التغيير |
|---|---|
| أعمدة `vendor_licenses` (إضافية nullable متوافقة) | `edition`، `deployment_type`، `feature_set_code`، `update_channel`، `payload_version DEFAULT 1` |
| أعمدة `vendor_plans` (إضافية) | `feature_set_code`→، `allowed_deployments JSON`، `trial_defaults JSON` (مدة/حدود/تمديدات) |
| `vendor_feature_sets` 🆕 | code؛ modules JSON؛ flags JSON؛ limits JSON؛ إصدار مرقم؛ مدقّق باعتماديات I قبل الاعتماد |
| `vendor_provisioning_orders` + `..._steps` 🆕 | مرآة الشركة لسير F: عميل→فندق→مراحل/بوابات/توقيعات تسليم |
| `vendor_license_events` 🆕 | المرآة المزدوجة الإلزامية لـ`license_events` (نفس serial — LIC §14) |

### M-3. ما تغيّر في الإجماليات الرسمية
147 جدولاً المستهدف بمرحلة 2أ (119+28) **+ 11 فندق تجاري + 4 شركة = 162 جدولاً مستهدفاً نهائياً** (مع إعادة استخدام 2 من الـ28 — لا إزدواج). صفر تعديل كاسر؛ صفر حذف عمود؛ كل الأعمدة الجديدة nullable/بافتراضات.

## N — تغييرات الـ API (المتطلب 28)
> كل نقطة تلتزم «قانون الكتابة» D من ملف 12 (مسار `/api/v1` للجداد · عقد أخطاء · RBAC مصرّح · Idempotency · تدقيق). «تعديل» = non-breaking (حقول استجابة إضافية فقط).

### N-1. قاعدة الفندق — جديد ≈18 + موجود مستعار
| الحزمة | النقاط |
|---|---|
| القدرات | `GET /api/org/capabilities` (فعّالة+أسباب+اعتماديات) · `GET /api/org/capabilities/{code}` (تفصيل قدرة) |
| المعالج 28 | `GET/PUT /api/onboarding/steps` (تقدم قابل استئناف على `onboarding_progress` من 13-B) · `POST /api/onboarding/seal` (محضر ختم موقّع) |
| ترخيص | `POST /api/license/trial-extension-request` · `POST /api/license/apply-bundle` (رزمة موقعة: تجديد/تمديد/ميزة/نشر — موحدة بـtype) · `GET /api/license/events` |
| تحديثات | `GET /api/updates/available` · `POST /api/updates/stage` · `POST /api/updates/apply` · `POST /api/updates/rollback` · `GET /api/updates/runs` |
| دعم | `GET/POST /api/support/sessions` · `POST /api/support/sessions/{id}/revoke` · `GET /api/support/diagnostics-bundle` (معقّمة) |
| نسخ | **النقاط الست الموثقة بملف 12-C (حالة/الآن/جدولة/سجل/تحقق/استعادة) كما هي** + `POST /api/backup/restore-test/run` |

### N-2. الفندق — تعديلات
`GET /api/license/status`: + edition/deployment_type/update_channel/capabilities badge payload (يبقى متوافقاً) · `POST /api/sync/receive`: يقبل نوع `CONTROL_BUNDLE` موقّعاً (قناة التحكم D-3: ترخيص/إبطال/تهيئة/إعلان تحديث) · `GET /api/org/tenant`: + بادج نسخة/تجربة للواجهة · نقاط الإعدادات الحساسة تُعلَّم بملكية J وتُقرأ بوصف «شركة-تدار» عند COMPANY_ONLY.

### N-3. الشركة (VND) — ≈13
Provisioning: `GET/POST /api/v1/provisioning-orders` + `POST .../{id}/steps/{n}/complete` + `POST .../{id}/seal` (4) · نشر: `POST /api/v1/clients/{id}/deployment-change` + `/approve` + `/verify-migration` (3) · تراخيص: `POST /api/v1/licenses/{id}/trial-extension` (1) · قدرات: CRUD `feature-sets` (2) + `GET /api/v1/editions/matrix` (1) · تحديثات: `POST /api/v1/releases/{id}/waves` إدارة الموجات (1) · 360°: توسعة عروض heartbeat الحالية بحقول (آخر نسخة موفقة/آخر اختبار استعادة/مستخدمون فعليون) (1).
**RBAC VND:** أدوار الشركة الأربعة (MASTER §5) تُفصَل صلاحياتها صراحةً على هذه النقاط؛ التعليق/الإيقاف يتطلب نقطة موافقة ثنائية (شخصان — LIC §13).

## P — خطة الترحيل (Migration) ودمج الخارطة
### P-1. المراحل M0..M5 (كل مرحلة قابلة للشحن منفردة وآمنة التراجع)
| المرحلة | المحتوى | شرط خروج | التراجع |
|---|---|---|---|
| **M0** قارئ v2 المتوافق | تدريس الحقول الجديدة اختيارية بافتراضات آمنة؛ تراخيص v1 تعمل كما هي؛ اختبار: كل ملف ترخيص صادر تاريخياً يُقبل | صفر رفض لملفات v1 بالاختبار | إلغاء الميزة=إيقاف القراءة الموسّعة فقط |
| **M1** القاعدة التجارية | جداول M-1/M-2 additive + قناة CONTROL_BUNDLE + license_events مزدوج | هجرات خضراء على نسخة عميل حقيقية؛ لا تغيير سلوك ظاهر | الجداول جديدة أصلاً = إيقاف استهلاكها فقط |
| **M2** محرك الاستحقاق | require_feature معمّّم + `/api/org/capabilities` + ترشيح التنقل + قالب القفل | **افتراضي الهجرة: كل عميل قائم يحصل Effective = ما يستخدمه فعلاً اليوم** ⇒ صفر شاشة تختفي عند عميل موجود (اختبار مصفوفة أدوار×وحدات) | علم تعطيل feature-flag بالإصدار |
| **M3** التثبيت والتسليم | المعالج 28 + provisioning + قوالب + سير F | تثبيت فندق sandbox من صفر→تسليم ≤زمن الهدف (§F-3) | المعالج لا يُشغَّل إلا على تثبيتات جديدة |
| **M4** التحديثات والنسخ | مدير تحديثات (قناة stable أولاً) + ربط P0-3 الفعلي بـbackup_jobs + BACKED_UP إلزامي | تحديث تجريبي→تراجع ناجح E2E على بيئة مكررة | الحزم موقعة وقابلة للتجاهل؛ لا إجبار |
| **M5** النسخ التجارية | editions K + قمع تجارب + بطاقة 360° المستكملة + مفتاح قصير | تدفق Trial→Converted كامل بعميل تجريبي | إصدار حمولات edition سابقة الطراز يبقى يعمل |

### P-2. ترحيل العملاء الحاليين (التجريبي/الطيار)
1. جرد تلقائي: وحدات مستخدمة فعلاً + مستخدمون نشطون + فروع ← توليد حمولة v2 مكافئة (`edition=COMMERCIAL` وfeature_set يطابق الاستعمال) — **لا فقدان ميزة قائمة، ولا بيانات تمُس**.
2. `deployment_type` الموروث: ON_PREM افتراضياً؛ من فعّل اقتران مزامنة فعلي ⇒ HYBRID.
3. تجربة قائمة (TRIAL بملف v1) تستمر بمدتها الأصلية؛ تكتسب فقط واجهة G الجديدة عند المراحل.

### P-4. قرارات جديدة تُرفع لاعتماد المالك (تنضم لسجل القرارات — README)
13. **سجل القدرات ككود موقّع لا جدول فندق** (مانع عبث بنيوي — M-1).
14. **قناة التحكم عبر `sync/receive` بنوع CONTROL_BUNDLE** بدل خدمة منفصلة (D-3 — أبسط سطحاً).
15. **سياسة PAST_DUE الآلية:** READ_ONLY آلي بعد N يوم تأخر مع بقاء الإيقاف بشرياً مزدوجاً (LIC §8).
16. **نطاق ترقيم SCR-CMR/VND-CMR** لتوسعات التجارية (O).
17. **اختصار Escrow مفاتيح النسخ:** يُقدَّم خياراً تعاقدياً مستقلاً أم يُمنع؟ (BACKUP §9 — توصية الفريق: خيار بعقد مستقل).
