## 1. أنواع النشر الثلاثة — التفريع التقني الفعلي (المتطلب 1)
> النموذج الرسمي وجدول القرار بالمرجع الأم §2. هنا: **ما الذي يختلف تقنياً فعلاً** في كل نمط.

| المكوّن | A — ON_PREM | B — CLOUD | C — HYBRID |
|---|---|---|---|

## 2. تغيير نوع النشر — فعل شركة بسير نقل بيانات موثق (قاعدة 7/J)
`طلب عميل مبرر → قرار شركة (مالك + مدير اشتراكات) → خطة ترحيل مؤرخة → نسخة كاملة مشفرة قبل أي شيء →` **`تصدير موقّع` (manifest بأعداد كل جدول حاكم + hash) `→ نقل → استيراد → تحقق مطابقة آلية (أعداد/مجاميع/ hash سلسلة تدقيق) → نافذة تجميد كتابة (READ_ONLY مؤقت معلن) → إشهار تحوّل بحدثين متطابقين بالجانبين → إصدار حمولة v2 جديدة بالنمط الجديد → إيقاف/فك اقتران النمط القديم (SEVERED موثق)`** — التراجع: النسخة الأصلية تبقى قانونية حتى محضر قبول العميل؛ أي فشل تحقق = إلغاء آمن بلا فقدان.

## 5. إعادة تقييم المزامنة الهجينة (المتطلب 13)
**الموجود المُثبت (17 نقطة ✅):** اقتران بمفاتيح (`pair`)، التقاط ذري Outbox بنفس معاملة العمل (main.py:startup)، دفع/سحب، backfill استدراكي ✅، صندوق تعارضات بحسم بشري ✅، قناة USB كاملة ✅، نبض ✅، سحب تراخيص/إبطالات ✅. **الأحكام:**
1. **تغطية الكيانات = الفجوة الوحيدة الجوهرية** → P0-2 (فوليوهات/فواتير نزلاء/فواتير POS/حجوزات/حركات مخزون/مسيرات/ماسترات §1) — تُدار بجدول سجل كيانات رسمي: كل كيان له (event_key حتمي، مفتاح ترتيب، سياسة تقشير حمولة).
2. **قرار D-3 النهائي:** تيار مفرد مرتب بأرقام تسلسلية (الكود الحالي) **+ قناة تحكم خارج النطاق** للترخيص/النبض/الإبطال/حزم التهيئة الموقعة (`sync/receive` يقبل نوع CONTROL_BUNDLE موقّعاً) — أصغر مساحة وأمتن من طوابير أولويات؛ يُغلق C-10 رسمياً.
3. **قابلية الاستئناف:** دفعات مرقمة + إقرار تطبيق ⇒ انقطاع وسط دفعة يعاد من آخر إقرار بلا ازدواج (idempotent بمفاتيح أحداث ✅) — يُوثق كضمان SLA داخلي.
4. **عتبات الصحة:** HEALTHY ≤ 15 دقيقة تأخر و≤200 حدث معلق؛ LAGGING فوقها (لوحة+NTF-SYS)؛ CONFLICTED بشري فقط ✅.
5. **متانة النبض عند الآلاف:** Backoff بإزاحة عشوائية (موروث) + حمولة ميتاداتا فقط (خصوصية §BACKUP-9) + تجميع rollups يومية للوحة (لا JOIN بين مستأجرين — قاعدة MASTER §7).
6. **اختبارات فقد إلزامية:** سيناريو فقد 5% أحداث + انقطاع 72 ساعة + USB متكرر — بوابة قبول P0-2 (اختبارات 15).

## 6. مدير التحديثات (المتطلب 23) — آلة الحالات §4.7
1. **الحزمة:** ملف تحديث موقّع (رمز + ترحيلات + بيان إصدار)؛ `vendor_releases`/`vendor_client_updates` ✅ تُدار جهة الشركة؛ جهة الفندق جديدة كلها (`update_packages`/`update_runs` — CHANGE §M).
2. **القنوات:** `stable` (افتراضي) / `beta` (مختارون)؛ النشر موجات: كانار 5% → 30% → الكل؛ قناة العميل من الحمولة (`update_channel`).
3. **التدفق لدى الفندق:** إعلان توفر (قناة/U SB) → **STAGE** (تنزيل+تحقق توقيع+فحص متطلبات) → **BACKED_UP إلزامي** (لا تطبيق بلا نسخة موفقة محققاً فتحها) → APPLY (خدمة تتوقف لحظياً/ترحيلات **additive فقط**) → HEALTH_CHECK (أبواب فحص: إقلاع/ترخيص/قيد ذهبي/مزامنة) → DONE أو **ROLLED_BACK**.
4. **التراجع:** بما أن الترحيلات additive ⇒ الرجوع = استرجاع نسخة ما قبل التحديث + إعادة حزمة الرمز السابقة؛ يُوثق سبب التراجع وتُجمّد موجة النشر تلقائياً عند عتبة فشل (مثلاً ≥2% من الموجة).
5. **ممنوعات مطلقة:** لا `git pull` ولا أوامر سطر بجهة العميل؛ لا تحديث كاسر للمخطط (كسر = إصدار رئيسي بنافذة صيانة متعاقدة)؛ لا DONE بلا HEALTH_CHECK.
6. **الواجهة:** SCR-CMR-004 (توفر/قناة/تاريخ/سجل runs/زر تطبيق/تراجع) + تنبيه NTF عند تراجع.

## 7. قوالب التهيئة الجاهزة (المتطلب 24)
> قالب = ملف واصف JSON موقّع من الشركة: وحدات+قدرات افتراضية + إعدادات النطاقات + خريطة ربط + شاشات مقترحة. **أولوية الدمج:** قيمة صرّح بها الفندق في المعالج > تجاوزات الحمولة > القالب > افتراضات النظام.

| القالب | الهوية | أبرز ما يضبطه |
|---|---|---|
| **فندق صغير** (≤30 غرفة) | HOTEL+ACCOUNTING (+POLICE تبعاً) | صندوق واحد، ضرائب مبسطة، بلا مخزون/POS، تقارير يومية أساسية |
| **فندق + مطعم** | +POS+INVENTORY | منفذان (مطعم/قهوة)، طابعات تصنيف، ربط تكلفة مبيعات، مخزن رئيسي+مطبخ |
| **فندق كامل الخدمات** | +HR+ASSETS(+BANQUETS لاحقاً) | مسيرات وإهلاكات، خدمات غسيل/نقل، موازنات تشغيلية |
| **مؤسسي/سلسلة** | +MULTIBRANCH (+CLOUD_SYNC وHYBRID إلزاماً) | فروع متعددة، توحيد ماسترات، تقارير مجمعة، أدوار مقيدة بالفروع (P3 صفّي) |

القوالب تُدار بلوحة الشركة (إصدار/نسخة/توقيع) وتُستهلك بخطوة اختيار القالب ضمن المعالج (الخطوة 0 عملياً)؛ تعديل أي قيمة لاحقاً طبيعي — القالب **بذرة لا قيد**.

## 8. الدعم عن بُعد بموافقة صريحة (المتطلب 25)
**الخصائص الخمس الملزمة لأي جلسة:** (1) **موافقة صريحة** من مالك الفندق/مدير النظام داخل النظام (DLG-CMR-001 ببيان الطلب: من؟ لماذا؟ ماذا؟) (2) **نطاق مُعلن**: شاشات/وحدات مسموحة فقط (3) **مدة قصوى** زمنية تُقفل تلقائياً (4) **تدقيق كامل**: كل شاشة عُرضت وفعل نُفذ بسجل `support_session_events` (5) **إلغاء فوري** بزر فندقي دائم الظهور أثناء الجلسة.
- **الصلاحيات:** جلسة الدعم تمنح دور «مصاد» Read-mostly؛ **محرومة بنيوياً من:** عمليات الترخيص، تصدير معرّفات كاملة (مقنّعة)، حذف/تعديل مالي، وبيانات النزلاء الحساسة إلا بإذن تصعيد ثانٍ (LIC T-12).
- **البديل الأول دائماً — حزمة تشخيص معقّمة:** زر «صدّر حزمة دعم» يجمع: سجلات أخطاء، حالة ترخيص/مزامنة/نسخ، عدادات أداء، نسخة الإصدار — **بلا أي بيانات أعمال أو PII** (قائمة بيضاء حقول صريحة) — تُرفع بتذكرة VND ✅ وتحل أغلب الحالات بلا جلسة (CR-09).
- لا وصول SSH/قاعدة مباشر من الشركة إطلاقاً؛ القناة الوحيدة: جلسة النظام نفسه.
