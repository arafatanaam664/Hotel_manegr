# FEATURE & ENTITLEMENT ARCHITECTURE — معمارية المزايا والاستحقاقات (المخرَجات I · J + التجريد المحاسبي + UX بالدور)

> **المرحلة 2ب — تصميم فقط؛ لا كود.** التاريخ: 2026-08-07 | تغطي المتطلبات: 4, 5, 6, 7, 8, 9, 17, 18
> **قاعدة المالك الحاكمة:** الاستحقاق ليس إخفاءً بالواجهة — يُفرض خادمياً؛ ولا تجاوز لإعدادات الشركة من العميل؛ ولا مسار API يلتف على الاستحقاق. المحرك القائم (`require_module` ✅) يُعمَّم إلى `require_feature` — توسعة لا استبدال.

## 1. تصنيف عناصر النظام الأربعة (المتطلب 4)
| الطبقة | التعريف | الأمثلة | من يصدرها | أين تُنفَّذ |
|---|---|---|---|---|
| **MODULE وحدة** | حزمة أعمال كبرى مستقلة البيع | السبع الحالية ✅ `MODULES_ALL`: ACCOUNTING/HOTEL/POS/INVENTORY/HR/ASSETS/MULTIBRANCH | الحمولة الموقعة | حارس موجهات ✅ `main.py:151-162` |
| **CAPABILITY قدرة** | ميزة دقيقة قابلة للبيع/القفل داخل الوحدات | GROUPS, BANQUETS, LAUNDRY, KDS, ADVANCED_REPORTS, CLOUD_SYNC, REMOTE_BACKUP, OTA, WHATSAPP, API_ACCESS, PAYROLL… | الحمولة (feature_set + overrides) | `require_feature` معمَّم (§3) |
| **PERMISSION صلاحية** | فعلٌ على مورد داخل دور | 121 صلاحية (ملف 10) | مالك الفندق (RBAC) | `deps.get_principal` ✅ |
| **SETTING إعداد** | قيمة تشكيل سلوك | 13 نطاق إعداد (ملف 09) | بمصفوفة الملكية J (§6) | نقاط org API + قناة التحكم |

**العلاقات الحاكمة:** `Entitlement ⊆ شرط الدور` — القدرة المقفولة تُظهر الشاشة مقفلة لمن له صلاحية؛ والصلاحية الناقصة تخفيها حتى لو القدرة مفتوحة. منح قدرة **لا يمنح صلاحية** (يذهب طلب الصلاحية لمالك الفندق)؛ ومنح صلاحية على قدرة مقفولة يظهر صفحة القفل (§5) — أبداً 403 خام كتجربة نهائية.

## 2. محرك الاستحقاق — المجموعة الفعّالة (المتطلبان 5/6)
**Effective = (افتراضيات النسخة K) × (الخطة Plan بجهة الشركة ✅) × (تجاوزات الحمولة الموقعة overrides)**
- **المصدر الوحيد:** الحمولة الموقعة (v2 — LIC §3) المخزنة `payload_signed` ✅؛ لا جدول قابل للكتابة بالفندق يغير استحقاقاً (T-03).
- **اللحظات الحاكمة:** إصدار/تجديد حمولة · تبديل ميزة بالقناة الرسمية (LIC §10) · دخول READ_ONLY/SUSPENDED (تقليص آلي آلة §4.1: القراءة فقط فوق كل شيء).
- **الخوارزمية (وصفياً):** `فعّالة = defaults(edition) ∪ modules(plan) − مقفّل_بالحالة ـ ثم تُطبق overrides (إضافة/حذف صريحة) ـ ثم يُغلق بمدقق الاعتماديات I: أي قدرة فقدت متطلبها تُسقط هي أيضاً وتُذكر بالسبب`.
- **العرض:** `GET /api/org/capabilities` 🆕 (CHANGE §N) يرجع لكل عنصر: `effective=true/false` + **سبب الحالة** (غير مشمولة بالنسخة/بالخطة/معلّقة باعتمادية/مقيدة بحالة ترخيص) + اعتمادياتها — تستهلكه الواجهة للتنقل والصفحات المقفلة؛ ولا تبنى الواجهة استنتاجها الخاص أبداً.

## 3. الإنفاذ الخادمي — تعميم require_module → require_feature
| نقطة الإنفاذ | النمط | مثال |
|---|---|---|
| مستوى موجّه | كما اليوم بالـdependencies ✅ | module=POS على pos.router (يبقى) |
| مستوى نقطة | `@require_feature('BANQUETS')` على نقطة/مجموعة | توليد فاتورة وليمة |
| منطق عميق (خدمة) | فحص داخل الخدمة لحدث متفرع | منع إنشاء **فرع ثانٍ** إلا بـMULTIBRANCH (يُسدّ الفجوة الموثقة GAPS-6) · منع جدولة قناة OTA بلا OTA |
| مدقق تهيئة (قراءة) | فحص مجموعة الإعدادات عند الختم | يحذّر: LAUNDRY مفعل بلا INVENTORY |
عقد الاستجابة الموحد: 403 `{error:{code:'LIC.FEATURE_DISABLED', message_ar, details:{feature, reason, upgrade_hint}}}` — الواجهة تترجمها لصفحة §5 ولا تعرض نصاً خاماً. **حظر صريح:** لا يُقبل أي معامل `?force=` أو `role=` من العميل يلتف على الإنفاذ؛ الاختبارات تتضمن محاولة تجاوز API مباشرة (اختبار عبث إلزامي بكل قدرة — ملف 15).

|---|---|---|
| HOTEL | ACCOUNTING | كل فوليو/ليلة قيد ✅ (ترحيل آلي قائم) |
| POS | ACCOUNTING | مبيعات/ورديات قيود ✅ |
| HR | ACCOUNTING | استحقاقات/مسيرات قيود |
| ASSETS | ACCOUNTING | إهلاكات قيود ✅ |
| POLICE | HOTEL | مركّب على حارس HOTEL ✅ (D-2) |

## 5. القدرة المقفلة ومسار الترقية (المتطلبان 17/18)
1. **صفحة القفل الموحدة (SCR-CMR-002 — قالب واحد):** اسم الميزة + ماذا تفعل للفندق + **سبب القفل الدقيق من capabilities API** (غير مشمولة بخطتك «أساسية» / معلّقة باعتمادية: تتطلب تفعيل المخزون / مقيّدة بحالة الترخيص) + زران: «اطلب الترقية» و«معلومات الخطط».
2. **طلب الترقية (DLG-CMR-002):** ينشئ طلباً لدى الشركة (تذكرة Vendor ✅ بنوع UPGRADE) + إشعار مبيعات — لا وعود آلية بسعر.
3. **القرار والتفعيل:** اعتماد شركة ← إصدار حمولة جديدة ← تسليم قناة/ملف ← إشعار واجهة «أُضيفت: إدارة الولائم» ← فوري بلا إعادة تشغيل (إعادة تقييم `evaluate` ✅)؛ التعطيل متماثل مع بقاء البيانات قراءة-فقط (LIC §10).
4. **انضباط البيع (CR-05):** صفحة القفل تعرض فقط ما هو قابل للبيع فعلاً بالنسخة (صفحة REMOTE_BACKUP تشرح العقد المطلوب — لا تبيع حلماً ممنوعاً بنيوياً).

## 6. مصفوفة الملكية (المخرَج J) — من يملك كل قرار (المتطلب 7)
> أربع طبقات صلاحية-ملكية. **القاعدة البنيوية الأقوى: عناصر COMPANY_ONLY لا توجد لها نقطة كتابة أصلاً في API الفندق — «لا مسار = لا تجاوز»** يتفوق على أي فحص صلاحية قابل للخطأ.

| الطبقة | التعريف | آلية التغيير الوحيدة | أمثلة |
|---|---|---|---|
| **USER_EDITABLE** | تفضيل شخصي لا أثر تشغيلياً | واجهة المستخدم مباشرة | لغة عرض، كثافة جدول، مفضلة تقارير (user_prefs — 13-B) |
| **HOTEL_ADMIN** | قرار تشغيلي للمنشأة | API الفندق + صلاحية settings.manage لدور مالك/مدير | سياسات حجز/ودائع/حد ائتمان، ضرائب وعملات (P1-08)، طابعات، خريطة غرف، أدوار المستخدمين |
| **COMPANY_ONLY** | قرار تجاري/تعاقدي | **حزمة تهيئة موقعة عبر قناة التحكم (sync CONTROL_BUNDLE — D-3) + تدقيق جانبين** | deployment_type، النسخة edition، الوحدات/القدرات، max_users/max_branches، مدة التجربة وتمديدها، REMOTE_BACKUP، update_channel، سياسة الإبطال، عتبات الأمان الحرجة (مدة الجلسة الدنيا/قفل الدخول) — **ينسخ نفسه بنبض الحالة للوحة** |
| **SYSTEM_IMMUTABLE** | ثابت هندسي | تغيير كود بإصدار موقّع فقط | خوارزمية التوقيع، مرساة الساعة، عقد الأخطاء، تسلسل الأحداث |

**جدول نطاقات الإعدادات الـ13 (ملف 09) × المالك (ملخص):** الهوية والترويسة→HOTEL_ADMIN (رقم السجل الضريبي بعد ختم الإقرار الأول يقيّد تعديله بموافقة مزدوجة فندقية موثقة) · السياسات التشغيلية→HOTEL_ADMIN · الضرائب/العملات→HOTEL_ADMIN · الأمان المحلي (تعقيد كلمات/MFA أدواره)→HOTEL_ADMIN **بأرضية COMPANY_ONLY** لا يُنزِل عنها (مثلاً لا تعطيل قفل الدخول) · النسخ والاستعادة→HOTEL_ADMIN للوجهات/الجدولة مع **إلزامية COMPANY_ONLY** (لا مسار لتعطيل التشفير أو خفض GFS عن الحد الأدنى) · الترخيص/النشر/التحديثات→COMPANY_ONLY عرض-فقط للفندق · التكاملات الخارجية→HOTEL_ADMIN للمفاتيح **بعد بوابة قدرة** (OTA تتطلب القدرة). **الواجهة تعكس الملكية:** إعدادات الشركة تظهر بقفل رمادي وبادج «تُدار من شركة سِجِلّ — اطلب تعديلها» (زر طلب يرفع تذكرة) — لا حقل معطّل بلا تفسير.

## 7. طبقة التجريد المحاسبي (المتطلب 8) — «أعمال فوق قيود»
**الموجود:** محرك قيود مزدوج صارم ✅ + ترحيل آلي من العمليات (تسكين/ليلة/فاتورة POS/وردية تنشئ قيودها) + خريطة ربط الأحداث الـ27 (خطوة 21 بالمعالج). **المصمَّم فوقه:** طبقة مفردات أعمال تجعل غير المحاسب منتجاً والمحاسب مسيطراً:
| الدور | ما يراه ويصنعه | ما يحدث دفترياً (خفي عنه) |
|---|---|---|
| موظف استقبال | «سند قبض وديعة نزيل»، «فاتورة إقامة»، «إرجاع مبلغ» | قيد: صندوق/ذمم نزلاء بربط خريطة الأحداث ✅ |
| كاشير POS | «إغلاق وردية — توريد نقدية» | قيود مبيعات/توريد/فروقات صندوق ✅ |
| أمين مخزن | «سند صرف مطبخ»، «إشعار استلام» | قيود مخزون/تكلفة ✅ |
| مدير مالي/محاسب | يرى كل ما سبق **وقيوده**: يومية/أستاذ/ميزان + اقتراحات تصحيح بقيد عكسي موثق (لا تعديل صامت أصلاً ✅) | نفس المحرك الواحد — **مصدر واحد للحقيقة، مفردتان للعرض** |
**قواعد:** لا شاشة أعمال تسمح بصياغة قيد حر إلا لأدوار acc.*؛ كل مستند أعمال يعرض «أثره الدفتري» بتلخيص مبسط + زر «عرض القيد» لمن له الصلاحية؛ تقارير الإدارة بمفردات أعمال («إيراد الغرف») تُشتق من نفس الأرصدة لا من حسابات موازية (اتساق API↔Database — MASTER §10).

## 8. تجربة الاستخدام بالدور × الاستحقاق (المتطلب 9)
1. **معادلة التنقل الرسمية (تُبنى بمكوّن واحد):** `يظهر عنصر القائمة ⟺ (له صلاحية RBAC) ∧ (الوحدة/القدرة فعّالة)` — مورد واحد يغذي القائمة والشاشات (لا تشتيت ترشيح بين مكونات).
2. **ثلاث نتائج لكل دخول شاشة:** متاح كامل · **مقفل بسبب** (§5) · غير مرئي أصلاً (لا صلاحية). ممنوع الناتج الرابع: صفحة تُفتح ثم تفشل بـ403.
3. **تقليص الازدحام للأدوار الصغيرة:** كاشير POS يرى شاشة البيع/ورديته/إقفاله فقط؛ الهوسكيبينج (PWA لاحقاً) قائمتها مهامها — اللوحة التكيفية ✅ تتبع نفس المعادلة.
4. **بادج النسخة/التجربة بالترويسة (SCR-CMR-003):** «نسخة تجريبية — 12 يوماً» أو «أساسية» — مصدره `/api/license/status` ✅ الموسّع (CHANGE §N)؛ يضغطه الملاك لصفحة الاشتراك.
5. **الاتساق مع 403 الخادمي:** أي قدرة سبق ترشيحها وسُبقت بالواجهة (تابع محفوظ/رابط قديم) تلقى صفحة قفل §5 بواسطة مترجم أخطاء موحد — التجربة مغلقة من الطرفين.
